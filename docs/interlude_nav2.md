## 1. Nav2の部品

### 1-1. 移動ロボットの「行き先まで連れていく」仕組み

Nav2（Navigation2）は、ROS 2で、移動ロボットを地図の上の目的地まで自律で動かすためのパッケージ群である。フェーズ6で `ros-jazzy-navigation2` を導入したとき、実際には、次のような多くの部品がまとめて入っている。Nav2は、これらを組み合わせて、「今どこにいるか」「どこを通るか」「どう動くか」「困ったらどうするか」を分担する。

| 部品（パッケージ） | 役割 | フェーズ6 |
|---|---|---|
| 地図の配信（`nav2_map_server`） | 保存した地図の画像を読み、地図のトピックとして配る | 使っていない |
| 自己位置の推定（`nav2_amcl`） | 地図とLiDARの値を照らし合わせ、地図の上の自分の位置を推定する | 使っていない（PX4が位置を推定するため） |
| コストマップ（`nav2_costmap_2d`） | 障害物の地図を作る。層を重ねて作る | **使った**（障害物の層・膨らませる層） |
| 計画器（`nav2_planner` と、NavFn・Smac・Theta\*などのプラグイン） | 地図の上で、目的地までの経路を計画する | **使った**（NavFnをA\*で） |
| 制御器（`nav2_controller` と、DWB・MPPI・Regulated Pure Pursuitなどのプラグイン） | 経路に沿って進む速度の指令（`cmd_vel`）を、細かい周期で作る | 使っていない（自作のノードが、経路の少し先の点をPX4へ送った） |
| 経路の平滑化（`nav2_smoother`） | 計画した経路の角を滑らかにする | 使っていない |
| 困ったときの行動（`nav2_behaviors`） | その場で回る・後ろへ下がる・待つ、などの立て直しの動き | 使っていない |
| 全体の進行役（`nav2_bt_navigator`） | 「計画する → 進む → 失敗したら立て直す」の流れを、行動の木（ビヘイビアツリー、`nav2_behavior_tree`）で進める。目的地を受け取るアクション `navigate_to_pose` を持つ | 使っていない（自作のノードが、0.5秒ごとの計画の依頼と進み方を受け持った） |
| 経由点の巡回（`nav2_waypoint_follower`） | 経由点の並びを、順に回る | 使っていない |
| 速度の平滑化・衝突の監視（`nav2_velocity_smoother`・`nav2_collision_monitor`） | 速度の指令を滑らかにする。ぶつかりそうなら、指令を弱めたり止めたりする | 使っていない |
| 充電台への接近（`opennav_docking`） | 充電台などへ、決まった姿勢で近づいて止まる | 使っていない |
| ライフサイクルの管理（`nav2_lifecycle_manager`） | 部品の「設定」「有効化」を、決まった順に自動で行う | 使っていない（`ros2 lifecycle` のコマンドで手で行った） |
| Pythonから使う道具（`nav2_simple_commander`） | 上の部品を、Pythonの短いコードで操る | 使っていない |

### 1-2. ふつうの使い方の流れ

地面を走るロボットでのふつうの使い方では、次のようにつながる。

1. 地図の配信と自己位置の推定で、「地図の上のどこにいるか」（`map` → `odom` → `base_link` のTF）を得る。
2. 全体の進行役が、目的地をアクション `navigate_to_pose` で受け取る。
3. 進行役の行動の木が、計画器に経路を頼み、制御器に経路をたどらせる。制御器が出す速度の指令（`cmd_vel`）で、ロボットの車輪が回る。
4. 進めなくなったら、行動の木が、困ったときの行動（回る・下がる）と計画のし直しを試す。

フェーズ6は、この流れのうち、1をPX4の位置と自作のノードが送るTFに、2〜4を自作のノード `replan_flight` に置き換え、計画器とコストマップだけを借りた形である。

## 2. ほかに何に使えるか

### 2-1. 地面を走るロボット

Nav2の本来の用途である。たとえば、次のことが、設定とlaunchのファイルだけでできる。

| 用途 | 主に使う部品 |
|---|---|
| 地図を作る（SLAM。別のパッケージ `slam_toolbox` 等と組み合わせる） | コストマップ・地図の保存 |
| 作った地図の上で、指した目的地へ自律で走る | 1-2節のすべて |
| 経由点を順に回る（見回り・配送など） | 経由点の巡回 |
| 入ってはいけない場所・速度を落とす場所を、地図に描いて決める | コストマップのフィルタ（`KeepoutFilter`・`SpeedFilter`） |
| 充電台に戻って止まる | 充電台への接近 |
| 人やほかのロボットを避けながら走る | 制御器（MPPI等）と、コストマップの障害物の層 |

親プロジェクトの車両（2輪の車）も、LiDARと、オドメトリ（車輪の回転から求めた位置。`odom` のTF）を足せば、Gazeboの中で、この形で走らせられる見込みである。

### 2-2. ドローンに使うとき

Nav2は、地面の上を平面に動くロボットを前提にしている。この教材のドローンに使うときは、次の点に注意する。

| 点 | 内容 |
|---|---|
| 平面だけ | コストマップは2次元で、高さの向きの経路は計画しない。フェーズ6のように、決めた高さを保って水平に避ける形に限られる（3次元の障害物を扱う層（`VoxelLayer`）もあるが、計画は平面のまま） |
| 自己位置 | 位置はPX4が推定するので、自己位置の推定（AMCL）は要らない。フェーズ6のように、PX4の位置からTFを作って渡す |
| 速度の指令 | 制御器が出す `cmd_vel` は、機体の座標系（前・左）の速度と回る速さで、車輪のロボット向けに作られている（2輪の車なら、前後の速さと回る速さだけ）。使うなら、PX4へ送る速度の目標（`TrajectorySetpoint` の `velocity`。NED）に直すノードが要る。直すときは、機首の向きによる回転と、ENUからNEDへの変換の両方が要る。フェーズ6では、制御器を使わず、経路の少し先の点を位置の目標として送ることで、この変換を避けた |
| 困ったときの行動 | 「後ろへ下がる」等は、車輪のロボットの動きを前提にしている。ドローンでそのまま使える保証はない |

ドローンでも使いやすいのは、コストマップのフィルタである。たとえば、`KeepoutFilter` で地図に「入ってはいけない場所」を描くと、計画器は、その場所を通らない経路を引く。シミュレーションの中で、通ってほしくない区域を、地図で決める使い方ができる（フィルタには、地図の配信と、フィルタの情報を配る部品が要る。設定は、Nav2の文書の「Navigating with Keepout Zones」にある）。ただし、これは計画器が「その区域を通らない経路を引く」だけで、機体の動きを止める仕組みではない。フェーズ6の自作のノードは経路の1m先の点を目標にするので、角では区域を少し横切ることもある。実機での飛行禁止区域の扱い（法令や、PX4の側のジオフェンス）は、この教材では扱わない。

## 3. 安全に変えられるところ、変えてはいけないところ

### 3-1. 大前提

- **Nav2が入れたファイルは書き換えない**: `/opt/ros/jazzy` の下のファイルは、aptが管理している。書き換えるには管理者の権限が要り、次の更新で上書きされる。設定を変えたいときは、フェーズ6のように、自分のパッケージの中の設定ファイル（`~/px4_ws/src/drone_offboard/config/planner.yaml`）を変える。書き方の見本には、Nav2の既定の設定ファイル（GitHubの [`nav2_bringup/params/nav2_params.yaml`](https://github.com/ros-navigation/navigation2/blob/jazzy/nav2_bringup/params/nav2_params.yaml)。`ros-jazzy-navigation2` には含まれず、別のパッケージ `ros-jazzy-nav2-bringup` を入れたときに `/opt/ros/jazzy` の下に入る）を読む。
- **ここでの「安全」は、シミュレーションの中での話である**: 設定を変えて機体がぶつかっても、シミュレーションを起動し直せば元に戻る。実機の機体に同じ設定を使うことは、この教材では扱わない。
- **一度に1つだけ変える**: 変えたら、フェーズ6の6節と7節で動きを確かめ、結果を見てから次を変える。複数を同時に変えると、どれが効いたか分からなくなる。
- **変えた後のやり直し方**: 機体を着陸させてノードを止め、フェーズ6の5-1節（PX4のシミュレーションの起動し直し）からやり直す。飛行中に計画器だけを止めて起動し直すと、自作のノードは前の経路をたどり続け、その後に見えた壁を避けない（計画器の答えを待ったまま、次の計画を頼まなくなることがある）。設定ファイルは、計画器（T5）が `src` の下のファイルを直接読むので、ビルドし直さなくてよい。自作のノードのコードを変えたときは、フェーズ6の4-3節でビルドし直す。

### 3-2. 計画器とコストマップの設定（`planner.yaml`）

| 区分 | 設定 | 変えると何が変わるか |
|---|---|---|
| 変えてよい | `GridBased.use_astar` | 探し方（A\*か、ダイクストラ法か）。経路の形と計画の時間が変わる |
| 変えてよい | `publish_frequency`・`always_send_full_costmap` | RViz2へ地図を配る回数と形。計画には影響しない |
| 変えてよい | `expected_planner_frequency` | 計画が遅いときに警告を出す目安。計画そのものには影響しない |
| 変えてよい | `inflation_layer.cost_scaling_factor` | 障害物の周りのコストの下がり方。小さいほど、障害物から遠い所を通りたがる |
| 注意して変える | `GridBased.tolerance` | 目的地の格子が通れないときに、代わりの終点を探す範囲。大きくすると、目的地から離れた所で経路が終わり、自作のノードの「着いた」の判定（`REACHED_DIST`）に入らず、着陸しなくなることがある |
| 注意して変える | `resolution` | 格子の細かさ。細かくすると、計画に時間がかかる。粗くすると（例: 0.5）、壁2と壁1の間の約2.5mの隙間が格子に丸められ、通れなくなることがある |
| 注意して変える | `update_frequency` | 地図を更新する回数。下げすぎると、新しい壁が地図に載るのが遅れる |
| 注意して変える | `robot_radius`・`inflation_layer.inflation_radius` | 小さくすると、壁の近くを通る経路になり、ぶつかりやすくなる。大きくすると、狭い隙間を通れなくなり、「経路が見つからない」が出る |
| 注意して変える | `obstacle_max_range`・`raytrace_max_range` | 遠くの壁を、いつ地図に書き込むかが変わる。フェーズ6の6-1節の「角を回ると北回りに引き直す」の筋書きは、18mを前提にしている |
| 注意して変える | `width`・`height`・`origin_x`・`origin_y` | 地図の範囲。狭くすると、機体や目的地が地図の外に出て、計画が失敗する。フェーズ6の筋書きは、東の端が20mであることを前提にしている（フェーズ6の9節の課題1） |
| 注意して変える | `track_unknown_space`・`GridBased.allow_unknown` | まだ見ていない場所を通る経路を引くかどうか。引かない設定にすると、最初の計画で目的地に届かないことがある（フェーズ6の9節の課題3） |
| 注意して変える | `scan.clearing`・`scan.inf_is_valid` | `false` にすると、LiDARの光が通り抜けた格子や、何にも当たらなかった向きの格子が、「空いている」に戻らない。一度載った障害物が消えなくなる |
| 注意して変える | `min_obstacle_height`・`max_obstacle_height`（層と `scan` の両方） | 高さの範囲。上限を3m未満にすると、飛んでいる高さのLiDARの点がすべて捨てられ、壁が地図に載らない |
| 変えてはいけない | `scan.marking` | `false` にすると、LiDARの点が障害物として地図に載らず、機体が壁に向かって飛ぶ |
| 変えてはいけない | `observation_sources` と、その下の `scan:` の名前・`scan.data_type` | `observation_sources` の名前は、下の小見出しの名前と一致している必要がある。`data_type` は、届く値の型（`LaserScan`）と一致している必要がある |
| 変えてはいけない | `global_frame`（`map`）・`robot_base_frame`（`base_link`） | 自作のノードが送るTFの名前と、ノードが目的地に付ける座標系の名前（`goal.goal.header.frame_id`）と、一致している必要がある。LiDARの値の座標系（`link`）も、ノードが送る静的なTFの名前と一致している必要がある |
| 変えてはいけない | `scan.topic`（`/scan`） | `parameter_bridge` の付け替えた名前と、一致している必要がある |
| 変えてはいけない | `planner_server`・`global_costmap` を2回重ねる形・`ros__parameters` | Nav2のノードの名前と、ROS 2の設定ファイルの決まった書き方。崩すと、設定が読み込まれず、既定値で動く（エラーにならないことが多く、気づきにくい） |
| 変えてはいけない | `planner_plugins`（`["GridBased"]` の1つ） | 自作のノードは、どの計画器を使うか（`planner_id`）を指定せずに頼む。計画器を2つ並べると、どれを使うか決まらず、計画が失敗することがある。計画器を替えるときは、6節の課題1のように、`GridBased` の中身を入れ替える |
| 変えてはいけない | `plugin` の値（`nav2_navfn_planner::NavfnPlanner` 等）・コストマップの `plugins` の名前の並び | 導入されているプラグインの正確な名前と、下の層の小見出しの名前。1文字でも違うと、「設定」に失敗する |

### 3-3. 自作のノード（`replan_flight.py`）

| 区分 | 箇所 | 変えると何が変わるか |
|---|---|---|
| 変えてよい | `GOAL_ENU` | 目的地。壁の中や、地図の外を指すと、計画が失敗するか、`tolerance` の範囲の近くで終わる |
| 変えてよい | `REPLAN_LOG_DIFF` | ログの出方だけが変わる |
| 注意して変える | `ALTITUDE` | 飛ぶ高さ。上昇の判定（`climbed`）は `ALTITUDE` から0.3mを引いた高さで決まるので、0.3m以下にすると、地上で水平に動き出す。低くすると、TFに傾きを入れていないので、少し傾いただけでLiDARの光が地面に当たり、偽の障害物が地図に載る（フェーズ6の2-1節。3mで約10°）。高さの範囲の設定（3-2節）とも合わせる。壁の高さ（15m）を超えると、LiDARが壁を見なくなる |
| 注意して変える | `LOOKAHEAD` | 大きいほど速く滑らかに進むが、まだ見ていない壁の向こうに目標を置きやすくなる（フェーズ6のつまずきやすい点） |
| 注意して変える | `PLAN_PERIOD` | 長くすると、新しい壁への反応が遅れる（速くはならない）。フェーズ6の7節の `ros2 topic hz /plan` の値も変わる |
| 注意して変える | `REACHED_DIST` | 小さすぎると、`tolerance` で経路の終点がずれたときに、着陸しなくなる |
| 注意して変える | `RETRY_CYCLES` | Offboardへの切り替え・アーム・着陸の指令を送り直す間隔。合図の周期とは別で、フェイルセーフには関係しないが、短すぎると指令が多く流れる |
| 注意して変える | `choose_target` の機首の向き（`self.yaw = math.atan2(...)`） | 機首を目標の向きに向けるのは、LiDARが前を中心に270°しか測らず、進む向きを見ながら飛ぶためである。向きを固定すると、進む先が見えないまま飛ぶことがある |
| 変えてはいけない | `LIDAR_OFFSET` | 模型のLiDARの位置（[間章（センサ）](interlude_custom_sensor.md) の2-1節）。模型を変えない限り、変える理由がない |
| 変えてはいけない | `PERIOD`・`send_setpoint`・`engaged`・`on_timer` の切り替えの流れ | オフボード制御の約束（フェーズ3の2節）を守るための部分。合図が毎秒2回より遅くなる（`COM_OF_LOSS_T`）と、PX4がフェイルセーフに移る。送る順を変えると、切り替えが受け付けられなくなる |
| 変えてはいけない | `enu_to_ned`・`enu_yaw_to_ned`・`enu_position`・`on_position` の座標の変換 | ENUとNEDの変換（フェーズ0の8節）。取り違えると、機体が思わぬ向きへ飛ぶ |
| 変えてはいけない | `now_us`・TFの時刻 | 時刻の扱い（フェーズ6の2-4節）。フェーズ3の4-2節と同じ形を保つ。TFの時刻を変えると、地図にLiDARの点が載らなくなる |
| 変えてはいけない | アクションの名前（`compute_path_to_pose`） | 計画器のアクションの名前と、一致している必要がある |

## 4. 計画器を止めずに設定を変える

コストマップの設定の一部は、計画器を止めずに、実行中に変えられる（Nav2のコストマップの層が、実行中の設定の変更を受け付けるように作られているため）。フェーズ6の5節まで進め、離陸した直後、壁1の角を回る前に、T8で試す。半径は、小さくする向きで試す（大きくすると、壁2と壁1の隙間で「経路が見つからない」が出ることがある）。

```bash
# T8
ros2 param get /global_costmap/global_costmap inflation_layer.inflation_radius

ros2 param set /global_costmap/global_costmap inflation_layer.inflation_radius 0.8
```

**期待する結果**（想定）:

```text
$ ros2 param get /global_costmap/global_costmap inflation_layer.inflation_radius
Double value is: 1.2

$ ros2 param set /global_costmap/global_costmap inflation_layer.inflation_radius 0.8
Set parameter successful
```

RViz2の地図（`/global_costmap/costmap`）で、壁の周りの薄い色の範囲が狭くなり、その後の経路（`/plan`）が、壁に少し近い所を通るようになる。コストマップのノードの名前が `/global_costmap/global_costmap` と2回重なるのは、フェーズ6の3-2節のとおり、地図が計画器の中に、`global_costmap` の名前空間の `global_costmap` というノードとして作られているためである。

実行中に変えた値は、計画器を止めると消え、次に起動したときは設定ファイルの値に戻る。良い値が見つかったら、設定ファイルに書き写す。

`ros2 param set` が `Set parameter successful` と表示しても、その設定が実行中に効くとは限らない。ROS 2では、宣言されている設定なら、ノードが拒まない限り、値の書き換え自体は成功と表示される。地図の範囲（`width` 等）や格子の細かさ（`resolution`）、プラグインの名前などは、書き換えても、計画器を起動し直すまで効かないことが多い。効いたかどうかは、RViz2の地図や経路の変化で確かめる。効かない設定は、設定ファイルを直し、3-1節のやり直し方で試す。

## 5. まとめ

- Nav2は、地図・自己位置・計画・制御・立て直しを分担する部品の集まりで、フェーズ6は、その中の地図と計画だけを借りた。
- 地面を走るロボットなら、地図を作る・目的地へ走る・見回る・入ってはいけない場所を避ける、などが設定だけでできる。ドローンに使うときは、平面の計画であること、制御器の速度の指令をPX4の目標に直す必要があることに注意する。
- 設定を変えるときは、自分のパッケージの設定ファイルを変え、名前を合わせる必要がある所（座標系・トピック・ノード・プラグイン・観測の名前）と、オフボード制御の約束にかかわる所には手を付けない。数値は一度に1つずつ変えて、動きを確かめる。

## 6. 課題（任意）

1. 計画器を、NavFnから、Smac Planner（格子の上の探し方の一種）の2次元版に替える。`planner.yaml` の `GridBased` の `plugin` を `nav2_smac_planner::SmacPlanner2D` にし、NavFnだけの設定（`use_astar`）を消して、`tolerance` と `allow_unknown` を残す。3-1節のやり直し方で、フェーズ6の6節の経路の形を比べる。
2. 同じく、Theta\*（`nav2_theta_star_planner::ThetaStarPlanner`）に替える。Theta\*は、見通しのきく点どうしを直線で結ぶ探し方で、格子の向きに縛られない、折れ曲がりの少ない経路を引く。Theta\*には `tolerance` の設定が無いので、`GridBased` の中身は `plugin` と `allow_unknown` だけにする（目的地の格子が塞がっていると、計画が失敗する）。課題1の経路と比べる。
3. 4節の方法で、`inflation_layer.cost_scaling_factor` を1.0と10.0に変え、経路が壁からどれだけ離れるかを比べる。
4. Nav2の文書の「Navigating with Keepout Zones」を読み、フェーズ6の壁のワールドに「通ってほしくない区域」を足すには、どの部品と、どんなファイル（地図の画像と、その説明のファイル）が要るかを書き出す（作るところまではしなくてよい）。

## つまずきやすい点

- **設定ファイルを直したのに、動きが変わらない**: 計画器を起動し直していない（設定ファイルは、起動の後の「設定」のときにだけ読まれる）。または、設定の階層（字下げ）がずれて、別の名前の設定として読まれている。`ros2 param get` で、実際の値を確かめる。
- **`ros2 param set` が成功と出たのに、何も変わらない**: その設定は、実行中には効かない（4節）。設定ファイルを直して、3-1節のやり直し方で試す。
- **`ros2 param set` が失敗と出る**: ノードの名前（`/global_costmap/global_costmap`）、設定の名前（層の名前から始まる）、値の型（小数の設定に `1` ではなく `1.0` を渡す）を確かめる。
- **計画器を替えたら「設定」に失敗する**: プラグインの名前の綴り、または、その計画器が入っているか（`ros2 pkg list | grep nav2_smac_planner` 等）を確かめる。
