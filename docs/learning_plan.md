# 学習計画（PX4・Gazebo・ROS 2でドローンのシミュレーションを組み立てる）

[`dev/idea_origin.md`](../dev/idea_origin.md) の6つの段階（①〜⑥）を、学習の順番に並べ、各フェーズの内容・前提・完了条件をまとめたもの。ゴールと技術を選んだ理由は構想の文書に、決めた経緯は [`dev/qa_log.md`](../dev/qa_log.md) にある。この文書に出てくるドローンとPX4の用語（SITL・アーム・オフボード制御・Position mode・uXRCE-DDS等）は、構想の文書の4節に短い説明があり、フェーズ0で詳しく学ぶ。技術的な記述の出典は、構想の文書の7節にまとめている。

> **作成中である。** 手順書は、環境構築とフェーズ0〜3（3-0を含む）が作成済み（一部の表示は想定のまま）で、フェーズ4〜6と間章3つは下書きである。読み物の間章2つ（フライトコントローラとPX4の製品への組み込み、シミュレーションから実機へ）とTips集は作成済みである（5節の一覧）。フェーズの番号と必須・任意の範囲は決めたもので、状況に応じて柔軟に直す。各フェーズの前提と完了条件は案で、手順書を作るときに確かめて直す。

## 1. 目的とゴール

- **目的**: ドローンのシミュレーション環境を段階的に構築して動かし、PX4・Gazebo・ROS 2をつないで使えるようになる。
- **最初のゴール**: フェーズ1（段階①）。Gazeboの中のドローンを、PX4で離陸させ、移動させ、着陸させる。
- **最終ゴール**: フェーズ6（段階⑥）。2DのLiDARで飛行中に障害物を検知したら、経路を計画し直して、ぶつからずに目的地へ着く。

## 3. フェーズ計画

各フェーズの完了条件を満たしてから次へ進む。所要の目安は、手順書を作るときに見積もる。

### 環境構築

- **内容**: WSL2・Ubuntu 24.04・ROS 2 Jazzyの導入は、詳しい説明を親プロジェクトの [環境構築の手順書](https://github.com/SanghunIm1991/ros2MinimalPhysicalAi/blob/main/docs/setup_wsl2_ros2.md) に任せ、この教材の手順書には最低限の実行の手順（コマンドと期待する結果）だけを載せる。ROS 2のパッケージとしてのGazebo（`ros-jazzy-ros-gz`）の導入と確かめ方は、この教材の手順書で書く。その上に、PX4専用のPythonの仮想環境（`~/px4-venv`）、PX4のソース（`~/PX4-Autopilot`、v1.17）、PX4に付属する導入のスクリプト（`--no-nuttx`）、PX4のビルド、QGroundControl（WSLの中で動かすAppImage版）を導入する。
- **予備の実験**: PX4の導入のスクリプトが入れるGazebo公式の `gz-harmonic` と、`ros-jazzy-ros-gz` で入れたGazeboが共存するかを確かめる → 共存し、PX4のシミュレーションも動いた（2026-10-31）。
- **完了条件**: PX4のシミュレーション（`make px4_sitl gz_x500`）が起動し、Gazeboの中に機体が現れ、PX4のシェル（`pxh>`）が使え、QGroundControlが機体につながる。

### フェーズ0: ドローンとPX4の用語と仕組み（読み物）

- **内容**: マルチコプターが飛ぶ仕組み（プロペラの推力と姿勢の関係）、フライトコントローラとPX4の役割（機体の中の制御と、外の知能の分担）、SITL、アームと飛行モード（Position・Hold・Takeoff・Land・Return・Offboard 等）、地上局とMAVLink、uXRCE-DDS、座標系（PX4のNED・FRDと、ROS 2のENU・FLU）、安全の仕組み（アームの条件・フェイルセーフ）、実機では何が入れ替わるか（SITLでGazeboと中継がドライバの代わりをしていること。2026-11-03に追記）、この教材の完成形（どの部品をどのフェーズで学ぶか）。
- **完了条件**: 次のような問いに答えられる。プロペラの回転の速さを変えると、機体はどう傾き、どう進むか。なぜ地上局をつながないとアームできないのか。オフボード制御とPosition modeは、だれが行き先を決める点で違うか。同じ「北へ1m・上へ2m」の位置が、NEDとENUでどう書かれるか。

### フェーズ1: PX4とGazeboで飛ばす（段階①・最初のゴール）

- **内容**: PX4のシミュレーションを起動し、Gazeboの画面の見方（視点の動かし方・機体とワールドの見え方など）を確かめる。QGroundControlで離陸・地図の上の地点への移動・着陸を指示する。離陸と着陸、飛行モードの切り替えは、PX4のシェルのコマンドでも行い、モードが切り替わる様子を見る（シェルの `commander` のコマンドには地点を指す指示が無いので、移動はQGCの Go to location で行い、シェルでは離陸・帰還・着陸を指示する）。
- **前提**: 環境構築、フェーズ0。
- **完了条件**: 機体が離陸し、QGroundControlで指示した地点へ移動し、着陸する。そのときの飛行モードの変化を、QGroundControlやPX4のシェルの表示で確かめられる。

### フェーズ2: ROS 2から機体の状態を見る（段階②）

- **内容**: Micro XRCE-DDS Agentを導入して起動し、PX4のトピックをROS 2に出す。`px4_msgs`（`release/1.17`）をワークスペース `~/px4_ws` でビルドし、`ros2 topic` で機体の位置・姿勢などを見る。PX4のトピックを見るときにQoSの指定が要ること、座標系がNEDであることを、その場で説明する。実機でのAgentのつなぎ方（シリアルかEthernet）と、位置の値の出どころ（実機ではフライトコントローラのセンサ）も書く（2026-11-03に追記）。
- **予備の実験**: PX4 v1.17とROS 2 Jazzyの組み合わせで、`px4_msgs` がビルドでき、トピックを受け取れるか。
- **前提**: フェーズ1。親プロジェクトのフェーズ2の1-1・1-2・2-1・2-4・2-5節（ワークスペースの構成とビルドの流れ）。
- **完了条件**: QGroundControlで機体を動かすと、ROS 2で見ている位置の値が変わる。

### フェーズ3: ROS 2から指令して飛ばす（段階③）

- **内容**: 先にフェーズ3-0（復習のページ）で、自作のノードの骨組みとQoSの指定を、機体の高さを表示するノードで確かめる。本体では、`px4_ros_com` のオフボード制御のサンプルと同じ流れ（合図を送り続け、1秒たったらOffboardに切り替えてアームする）で、経由点を順に回るノードを一から書く（公式のPythonのサンプルは `main` のブランチにだけあり、v1.17の `_v1` の付くトピックの名前に合わないため。2026-10-31）。指令を送り続ける必要（約2Hzを下回るとオフボードから抜ける）と、ENUとNEDの変換を扱う。実機に載せるときの注意（合図は動いている証拠にすぎないこと、オフボード制御の間はPX4の衝突防止が働かないこと、自分でアームする作りは試験用であること）も書く（2026-11-03に追記）。
- **前提**: フェーズ2。親プロジェクトのフェーズ2の2-2・2-4・2-5節（パッケージの作り方）。ノードの基本・コマンドでの観察・QoSの復習は、フェーズ3-0で用意した（親プロジェクトのフェーズ3-1・3-2bは前提にしない）。
- **完了条件**: 機体が、ROS 2のノードの指令だけで、経由点を順に回って戻り、着陸する。

### フェーズ4: センサの値を見る（段階④）

- **内容**: 2DのLiDARを付けた機体（`x500_lidar_2d`）を、壁のワールド（`walls`）で起動する。LiDARの値を `ros_gz_bridge` でROS 2に中継し、RViz2で障害物の形として見る。`ros_gz_bridge` の使い方と、RViz2の使い方（起動・固定フレーム・距離のデータの表示、必要なら座標の変換）は、この手順書の中で書く。実機では、LiDARの値がドライバのノードから来ること（`ros_gz_bridge` がその代わりをしていること）と、合わせる点（座標系の名前・取り付け・時刻）も書く（2026-11-03に追記）。
- **予備の実験**: 専用のGPUが無いPCや、画面なしの起動でも、LiDARの値が出るか。
- **前提**: フェーズ3。親プロジェクトのフェーズ5-4（`ros_gz_bridge`）と間章（URDFとRViz2）は、車両の文脈が中心なので前提にせず、参考のリンクを置くだけにする。
- **完了条件**: 機体の周りの壁の形が、RViz2に表示される。機体を動かすと、表示される壁の位置が機体から見た向きに合わせて変わる。

### フェーズ5: 組み込みの衝突防止を試す（段階⑤）

- **内容**: PX4の衝突防止（Collision Prevention）のパラメータを設定し、QGroundControlからの操縦の入力（仮想ジョイスティック等）で、Position modeで壁に向かって飛ばす。減速・停止・向きの補正を観察し、センサが見ていない方向へは動けないことも確かめる。実機では、衝突防止の距離が、フライトコントローラにつないだ距離センサのドライバから来ることと、オフボード制御の間は衝突防止が働かないことも書く（2026-11-03に追記）。
- **前提**: フェーズ4。
- **完了条件**: 壁に向かって飛ばしても、機体が設定した距離の手前で止まる。組み込みの衝突防止ができることと、できないこと（経路を計画し直さない、Position mode以外（オフボード等）では働かない）を説明できる。

### フェーズ6: 計画し直して回避する（段階⑥・最終ゴール）

- **内容**: LiDARの値から障害物の地図を作り、目的地までの経路を計画し、障害物を見つけたら計画し直す。地図と経路の計画には、Nav2の計画器（`planner_server`）とコストマップを使う（2026-10-31、ユーザー判断で「Nav2を試す下書き」にした）。計画器に経路を頼み、経路をたどる目標をフェーズ3のオフボード制御で機体に送るノード（`replan_flight`）を、フェーズ3のノードを元に書く。フェーズ6-2の最後（5節。読み物）で、この構成を実機に移すとき、Gazeboから得ているデータがどこから来るか、動かすものをどこに置くか、PX4が気づかない止まり方と外のプログラムに要る見張りをまとめ、教材を一段落させる（2026-11-03に追記）。
- **予備の実験**: Nav2（`ros-jazzy-navigation2`）を導入し、計画器が、この教材の機体のTFとLiDARの値で地図を作り、経路を返すか。下書きは導入していない環境で書いたので、動かして確かめるのはこれから。うまくいかなければ、格子の地図とA\*の簡単な計画器を自作する案に戻る。
- **前提**: フェーズ3・4・5。ROS 2のアクションとライフサイクルは、手順書の中で説明する（親プロジェクトのフェーズ3-5は前提にしない）。
- **手順書の分け方**: 分量が多いので、手順書を2つに分ける。フェーズ6-1で、構成と仕組みを学び、Nav2を導入して計画器の設定ファイルと自作のノードを書き、ビルドする。フェーズ6-2で、起動して飛ばし、経路が引き直されるのを観察する（2026-11-01、ユーザー指示）。
- **完了条件**: まだ見ていない場所を空いているとみなした地図で、目的地までの経路を計画して飛び始め、飛行中にLiDARが新しい壁を見つけると、経路が引き直され（RViz2で経路が変わるのが見える）、機体が壁にぶつからずに回り込んで目的地に着き、着陸する。あわせて、この構成を実機に移すときに入れ替わるもの（Gazeboから得ているデータの実機での出どころ）を説明できる（2026-11-03に追記）。

### 間章: フライトコントローラの一般論と、PX4を製品に組み込むとき（任意・読み物）

- **内容**: フライトコントローラ一般が受け持つ仕事（ハードウェアとソフトウェアの層）と、主なフライトスタックのライセンスの違い。PX4の構成（2つの層・モジュール・設定の仕組み）。PX4を製品に組み込むときのワークフロー。機体に合わせて調整する部分と根幹の部分の境界（5つの層）。自作のソフトウェアとつなぐインターフェース（MAVLink・uXRCE-DDS・ROS 2のライブラリ・uORB・機体の部品）と選び方。
- **前提**: フェーズ0（フェーズ3まで終えていると、例が実感しやすい）。
- **完了条件**: 製品の機能を例に、変える場所がどの層に当たるかと、どのインターフェースでPX4とつなぐかを、理由とともに説明できる。

### 間章: 機体を定義する ― Gazeboの模型とPX4の機体の設定（任意）

- **内容**: シミュレーションの機体が、Gazeboの機体の模型・PX4の機体の設定・両者をつなぐ名前の約束でできていることを、PX4に付属するファイルで確かめ、機体のどこを変えるとどこを合わせるかを表にまとめる（任意の機体を定義する方法の見通し）。例として、360°のLiDARを付けた機体の模型を自作し、PX4のシミュレーションで使う。
- **前提**: フェーズ5（フェーズ6は終えていなくてよい）。
- **完了条件**: 自作の機体で、RViz2に真後ろの向きの点が表示され、衝突防止を有効にしたPosition modeで、真後ろへも動ける。

### 間章: Nav2の全体像と、安全に変えられるところ（任意）

- **内容**: Nav2の部品と役割を見渡し、フェーズ6で使った部品の位置づけと、ほかの用途（地面を走るロボット、立入禁止の区域など）、ドローンに使うときの限界を整理する。フェーズ6の設定とコードを、変えてよい・注意して変える・変えてはいけない、に分ける。

## 4. 手順書の方針

書き方の規則は、[`CLAUDE.md`](../CLAUDE.md) の「手順書（`docs/`）の書き方」節にある。要点は次のとおり。

- フェーズごとに1つ（必要なら分割）を、着手の直前に作る。
- コマンドを実行する手順の直後に「期待する結果」（表示の例と読み方）を置く。
- 図は、SVGを本文に表示し、同じ内容のmermaid版を折りたたみの中に置く。
- 親プロジェクトの手順書は、GitHubの絶対URLで参照し、どの節が前提かをREADMEの「読む順番」の「前提」の列に書く。車両の制御が中心の章など、文脈が違う章には前提として読者を送らず、要る部分をこの教材で書き直す（参考のリンクは置いてよい）。
- 公式の文書の文章は写さず、リンクと自分の言葉による要約にする。環境構築のコマンドのように、公式の文書の手順と同じになるものを載せるときは、出典・ライセンス・改変の有無を書く。
