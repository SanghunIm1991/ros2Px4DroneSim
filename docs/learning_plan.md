# 学習計画（PX4・Gazebo・ROS 2でドローンのシミュレーションを組み立てる）

[`docs/idea_origin.md`](idea_origin.md) の6つの段階（①〜⑥）を、学習の順番に並べ、各フェーズの内容・前提・完了条件をまとめたもの。ゴールと技術を選んだ理由は構想の文書に、決めた経緯は [`docs/qa_log.md`](qa_log.md) にある。

> **作成中です。** 手順書はまだありません。フェーズの番号と必須・任意の範囲は決めたもので、状況に応じて柔軟に直します。各フェーズの前提と完了条件は案で、手順書を作るときに確かめて直します。

## 1. 目的とゴール

- **目的**: ドローンのシミュレーション環境を段階的に構築して動かし、PX4・Gazebo・ROS 2をつないで使えるようになる。
- **最初のゴール**: フェーズ1（段階①）。Gazeboの中のドローンを、PX4で離陸させ、移動させ、着陸させる。
- **最終ゴール**: フェーズ6（段階⑥）。2DのLiDARで障害物を検知したら、経路を計画し直して、ぶつからずに目的地へ着く。

## 3. フェーズ計画

各フェーズの完了条件を満たしてから次へ進む。所要の目安は、手順書を作るときに見積もる。

### 環境構築

- **内容**: WSL2・Ubuntu 24.04・ROS 2 Jazzyと、ROS 2のパッケージとしてのGazebo（`ros-jazzy-ros-gz`）は、詳しい説明を親プロジェクトの手順書に任せ、この教材の手順書には最低限の実行の手順（コマンドと期待する結果）だけを載せる。公式の文書の手順と同じになるコマンドには、出典・ライセンス・改変の有無を書く。その上に、PX4専用のPythonの仮想環境（`~/px4-venv`）、PX4のソース（`~/PX4-Autopilot`、v1.17）、PX4に付属する導入のスクリプト（`--no-nuttx`）、PX4のビルド、QGroundControl（WSLの中で動かすAppImage版）を導入する。
- **予備の実験**: PX4の導入のスクリプトが入れるGazebo公式の `gz-harmonic` と、ROS 2のパッケージとして入っているGazeboが共存するかを確かめる。
- **完了条件**: PX4のシミュレーション（`make px4_sitl gz_x500`）が起動し、Gazeboの中に機体が現れ、PX4のシェル（`pxh>`）が使え、QGroundControlが機体につながる。

### フェーズ0: ドローンとPX4の用語と仕組み（読み物）

- **内容**: マルチコプターが飛ぶ仕組み（プロペラの推力と姿勢の関係）、フライトコントローラとPX4の役割（機体の中の制御と、外の知能の分担）、SITL、アームと飛行モード（Position・Hold・Takeoff・Land・Offboard 等）、地上局とMAVLink、uXRCE-DDS、座標系（PX4のNED・FRDと、ROS 2のENU・FLU）、安全の仕組み（アームの条件・フェイルセーフ）。
- **完了条件**: 上の用語を、自分の言葉で説明できる。
- 環境構築とは、どちらを先にしてもよい。

### フェーズ1: PX4とGazeboで飛ばす（段階①・最初のゴール）

- **内容**: PX4のシミュレーションを起動し、QGroundControlで離陸・地図の上の地点への移動・着陸を指示する。同じことを、PX4のシェルのコマンドでも行い、飛行モードが切り替わる様子を見る。
- **前提**: 環境構築、フェーズ0。
- **完了条件**: 機体が離陸し、指示した地点へ移動し、着陸する。そのときの飛行モードの変化を説明できる。

### フェーズ2: ROS 2から機体の状態を見る（段階②）

- **内容**: Micro XRCE-DDS Agentを導入して起動し、PX4のトピックをROS 2に出す。`px4_msgs`（`release/1.17`）をワークスペース `~/ros2_ws` でビルドし、`ros2 topic` で機体の位置・姿勢などを見る。PX4のトピックを見るときにQoSの指定が要ること、座標系がNEDであることを、その場で説明する。
- **予備の実験**: PX4 v1.17とROS 2 Jazzyの組み合わせで、`px4_msgs` がビルドでき、トピックを受け取れるか。
- **前提**: フェーズ1。親プロジェクトのフェーズ2（ワークスペースとパッケージのビルド）の範囲は、手順書を作るときに決める。
- **完了条件**: QGroundControlで機体を動かすと、ROS 2で見ている位置の値が変わる。

### フェーズ3: ROS 2から指令して飛ばす（段階③）

- **内容**: `px4_ros_com` のオフボード制御のサンプル（Python）を動かし、アーム・オフボードへの切り替え・上昇の流れを読む。そのサンプルを改造して、いくつかの経由点を順に回るノードを作る。指令を送り続ける必要（約2Hzを下回るとオフボードから抜ける）と、ENUとNEDの変換を扱う。
- **前提**: フェーズ2。親プロジェクトのフェーズ2・フェーズ3-1（PublisherとSubscriber）が必須の見込み。QoSの復習（親プロジェクトのフェーズ3-2b）と、親プロジェクトのフェーズ1の作り直しは、必要になったときに用意する。
- **完了条件**: 機体が、ROS 2のノードの指令だけで、経由点を順に回って戻る。

### フェーズ4: センサの値を見る（段階④）

- **内容**: 2DのLiDARを付けた機体（`x500_lidar_2d`）を、壁のワールド（`walls`）で起動する。LiDARの値を `ros_gz_bridge` でROS 2に中継し、RViz2で障害物の形として見る。
- **予備の実験**: 画面なしの起動でも、LiDARの値が出るか。
- **前提**: フェーズ3。`ros_gz_bridge` の説明は、この教材の中で書く。親プロジェクトのフェーズ5-4は車両の制御の文脈が中心なので前提にせず、参考のリンクを置くだけにする。
- **完了条件**: 機体の周りの壁の形が、RViz2に表示される。

### フェーズ5: 組み込みの衝突防止を試す（段階⑤）

- **内容**: PX4の衝突防止（Collision Prevention）のパラメータを設定し、QGroundControlの手動の操縦の入力（仮想ジョイスティック等）で、Position modeで壁に向かって飛ばす。減速・停止・向きの補正を観察し、センサが見ていない方向へは動けないことも確かめる。
- **前提**: フェーズ4。
- **完了条件**: 壁に向かって飛ばしても、機体が設定した距離の手前で止まる。組み込みの衝突防止ができることと、できないこと（経路を計画し直さない、オフボードでは使わない）を説明できる。

### フェーズ6: 計画し直して回避する（段階⑥・最終ゴール）

- **内容**: LiDARの値から障害物の地図を作り、目的地までの経路を計画し、障害物を見つけたら計画し直す。経路の経由点を、フェーズ3のオフボード制御で機体に送る。経路計画には、まず既存のパッケージを使えないかを実験で確かめ、足りなければ簡単な計画器を自作する。
- **予備の実験**: 経路計画に使える既存のパッケージの調査と試用。
- **前提**: フェーズ3・4・5。
- **完了条件**: 壁の向こうの目的地を指定すると、機体が壁にぶつからずに回り込んで着く。

## 4. 手順書の方針

書き方の規則は、[`CLAUDE.md`](../CLAUDE.md) の「手順書（`docs/`）の書き方」節にある。要点は次のとおり。

- フェーズごとに1つ（必要なら分割）を、着手の直前に作る。
- コマンドを実行する手順の直後に「期待する結果」（表示の例と読み方）を置く。
- 図は、SVGを本文に表示し、同じ内容のmermaid版を折りたたみの中に置く。
- 親プロジェクトの手順書は、GitHubの絶対URLで参照し、どの節が前提かをREADMEの「読む順番」の「前提」の列に書く。
- 公式の文書の文章は写さず、リンクと自分の言葉による要約にする。
