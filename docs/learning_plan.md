# 学習計画（PX4・Gazebo・ROS 2でドローンのシミュレーションを組み立てる）

[`docs/idea_origin.md`](idea_origin.md) の6つの段階（①〜⑥）を、学習の順番に並べ、各フェーズの内容・前提・完了条件をまとめたもの。ゴールと技術を選んだ理由は構想の文書に、決めた経緯は [`docs/qa_log.md`](qa_log.md) にある。この文書に出てくるドローンとPX4の用語（SITL・アーム・オフボード制御・Position mode・uXRCE-DDS等）は、構想の文書の4節に短い説明があり、フェーズ0で詳しく学ぶ。技術的な記述の出典は、構想の文書の7節にまとめている。

> **作成中です。** 手順書は、環境構築とフェーズ0・1のものがあります。フェーズの番号と必須・任意の範囲は決めたもので、状況に応じて柔軟に直します。各フェーズの前提と完了条件は案で、手順書を作るときに確かめて直します。

## 1. 目的とゴール

- **目的**: ドローンのシミュレーション環境を段階的に構築して動かし、PX4・Gazebo・ROS 2をつないで使えるようになる。
- **最初のゴール**: フェーズ1（段階①）。Gazeboの中のドローンを、PX4で離陸させ、移動させ、着陸させる。
- **最終ゴール**: フェーズ6（段階⑥）。2DのLiDARで飛行中に障害物を検知したら、経路を計画し直して、ぶつからずに目的地へ着く。

## 3. フェーズ計画

各フェーズの完了条件を満たしてから次へ進む。所要の目安は、手順書を作るときに見積もる。

### 環境構築

- **内容**: WSL2・Ubuntu 24.04・ROS 2 Jazzyの導入は、詳しい説明を親プロジェクトの [環境構築の手順書](https://github.com/SanghunIm1991/ros2MinimalPhysicalAi/blob/main/docs/setup_wsl2_ros2.md) に任せ、この教材の手順書には最低限の実行の手順（コマンドと期待する結果）だけを載せる。ROS 2のパッケージとしてのGazebo（`ros-jazzy-ros-gz`）の導入と確かめ方は、この教材の手順書で書く。その上に、PX4専用のPythonの仮想環境（`~/px4-venv`）、PX4のソース（`~/PX4-Autopilot`、v1.17）、PX4に付属する導入のスクリプト（`--no-nuttx`）、PX4のビルド、QGroundControl（WSLの中で動かすAppImage版）を導入する。
- **予備の実験**: PX4の導入のスクリプトが入れるGazebo公式の `gz-harmonic` と、`ros-jazzy-ros-gz` で入れたGazeboが共存するかを確かめる → 共存し、PX4のシミュレーションも動いた（2026-10-31）。
- **完了条件**: PX4のシミュレーション（`make px4_sitl gz_x500`）が起動し、Gazeboの中に機体が現れ、PX4のシェル（`pxh>`）が使え、QGroundControlが機体につながる。

### フェーズ0: ドローンとPX4の用語と仕組み（読み物）

- **内容**: マルチコプターが飛ぶ仕組み（プロペラの推力と姿勢の関係）、フライトコントローラとPX4の役割（機体の中の制御と、外の知能の分担）、SITL、アームと飛行モード（Position・Hold・Takeoff・Land・Return・Offboard 等）、地上局とMAVLink、uXRCE-DDS、座標系（PX4のNED・FRDと、ROS 2のENU・FLU）、安全の仕組み（アームの条件・フェイルセーフ）、この教材の完成形（どの部品をどのフェーズで学ぶか）。
- **完了条件**: 次のような問いに答えられる。プロペラの回転の速さを変えると、機体はどう傾き、どう進むか。なぜ地上局をつながないとアームできないのか。オフボード制御とPosition modeは、だれが行き先を決める点で違うか。同じ「北へ1m・上へ2m」の位置が、NEDとENUでどう書かれるか。

### フェーズ1: PX4とGazeboで飛ばす（段階①・最初のゴール）

- **内容**: PX4のシミュレーションを起動し、Gazeboの画面の見方（視点の動かし方・機体とワールドの見え方など）を確かめる。QGroundControlで離陸・地図の上の地点への移動・着陸を指示する。離陸と着陸、飛行モードの切り替えは、PX4のシェルのコマンドでも行い、モードが切り替わる様子を見る（シェルの `commander` のコマンドには地点を指す指示が無いので、移動はQGCの Go to location で行い、シェルでは離陸・帰還・着陸を指示する）。
- **前提**: 環境構築、フェーズ0。
- **完了条件**: 機体が離陸し、QGroundControlで指示した地点へ移動し、着陸する。そのときの飛行モードの変化を、QGroundControlやPX4のシェルの表示で確かめられる。

### フェーズ2: ROS 2から機体の状態を見る（段階②）

- **内容**: Micro XRCE-DDS Agentを導入して起動し、PX4のトピックをROS 2に出す。`px4_msgs`（`release/1.17`）をワークスペース `~/px4_ws` でビルドし、`ros2 topic` で機体の位置・姿勢などを見る。PX4のトピックを見るときにQoSの指定が要ること、座標系がNEDであることを、その場で説明する。
- **予備の実験**: PX4 v1.17とROS 2 Jazzyの組み合わせで、`px4_msgs` がビルドでき、トピックを受け取れるか。
- **前提**: フェーズ1。親プロジェクトのフェーズ2（ワークスペースとパッケージのビルド）のどの節を前提にするかは、手順書を作るときに決める。
- **完了条件**: QGroundControlで機体を動かすと、ROS 2で見ている位置の値が変わる。

### フェーズ3: ROS 2から指令して飛ばす（段階③）

- **内容**: `px4_ros_com` のオフボード制御のサンプル（Python）を動かし、アーム・オフボードへの切り替え・上昇の流れを読む。そのサンプルを改造して、いくつかの経由点を順に回るノードを作る。指令を送り続ける必要（約2Hzを下回るとオフボードから抜ける）と、ENUとNEDの変換を扱う。
- **前提**: フェーズ2。親プロジェクトのフェーズ2・フェーズ3-1（PublisherとSubscriber）が必須の見込み。ROS 2のコマンドでの観察とQoSの復習は、必要になったときにこの教材で用意する。
- **完了条件**: 機体が、ROS 2のノードの指令だけで、経由点を順に回って戻る。

### フェーズ4: センサの値を見る（段階④）

- **内容**: 2DのLiDARを付けた機体（`x500_lidar_2d`）を、壁のワールド（`walls`）で起動する。LiDARの値を `ros_gz_bridge` でROS 2に中継し、RViz2で障害物の形として見る。`ros_gz_bridge` の使い方と、RViz2の使い方（起動・固定フレーム・距離のデータの表示、必要なら座標の変換）は、この手順書の中で書く。
- **予備の実験**: 専用のGPUが無いPCや、画面なしの起動でも、LiDARの値が出るか。
- **前提**: フェーズ3。親プロジェクトのフェーズ5-4（`ros_gz_bridge`）と間章（URDFとRViz2）は、車両の文脈が中心なので前提にせず、参考のリンクを置くだけにする。
- **完了条件**: 機体の周りの壁の形が、RViz2に表示される。機体を動かすと、表示される壁の位置が機体から見た向きに合わせて変わる。

### フェーズ5: 組み込みの衝突防止を試す（段階⑤）

- **内容**: PX4の衝突防止（Collision Prevention）のパラメータを設定し、QGroundControlからの操縦の入力（仮想ジョイスティック等）で、Position modeで壁に向かって飛ばす。減速・停止・向きの補正を観察し、センサが見ていない方向へは動けないことも確かめる。
- **前提**: フェーズ4。
- **完了条件**: 壁に向かって飛ばしても、機体が設定した距離の手前で止まる。組み込みの衝突防止ができることと、できないこと（経路を計画し直さない、Position mode以外（オフボード等）では働かない）を説明できる。

### フェーズ6: 計画し直して回避する（段階⑥・最終ゴール）

- **内容**: LiDARの値から障害物の地図を作り、目的地までの経路を計画し、障害物を見つけたら計画し直す。経路の経由点を、フェーズ3のオフボード制御で機体に送る。経路計画には、まず既存のパッケージを使えないかを実験で確かめ、足りなければ簡単な計画器を自作する。
- **予備の実験**: 経路計画に使える既存のパッケージの調査と試用。
- **前提**: フェーズ3・4・5。
- **完了条件**: 障害物の無い地図で目的地までの経路を計画して飛び始め、飛行中にLiDARが壁を見つけると、経路が引き直され（RViz2で経路が変わるのが見える）、機体が壁にぶつからずに回り込んで目的地に着く。

## 4. 手順書の方針

書き方の規則は、[`CLAUDE.md`](../CLAUDE.md) の「手順書（`docs/`）の書き方」節にある。要点は次のとおり。

- フェーズごとに1つ（必要なら分割）を、着手の直前に作る。
- コマンドを実行する手順の直後に「期待する結果」（表示の例と読み方）を置く。
- 図は、SVGを本文に表示し、同じ内容のmermaid版を折りたたみの中に置く。
- 親プロジェクトの手順書は、GitHubの絶対URLで参照し、どの節が前提かをREADMEの「読む順番」の「前提」の列に書く。車両の制御が中心の章など、文脈が違う章には前提として読者を送らず、要る部分をこの教材で書き直す（参考のリンクは置いてよい）。
- 公式の文書の文章は写さず、リンクと自分の言葉による要約にする。環境構築のコマンドのように、公式の文書の手順と同じになるものを載せるときは、出典・ライセンス・改変の有無を書く。
