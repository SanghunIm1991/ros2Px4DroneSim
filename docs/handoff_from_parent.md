# 親プロジェクトからの申し送り

このプロジェクト（`ros2Px4DroneSim`）を立ち上げるときに、親プロジェクトの [`ros2MinimalPhysicalAi`](https://github.com/SanghunIm1991/ros2MinimalPhysicalAi) から引き継ぐ事項をまとめた文書。教材の本文ではなく、計画と記録の文書として扱う（READMEの「計画と記録の文書」に載せる想定）。

作成: 2026-10-30（親プロジェクトのセッションで作成）

## 1. 目的と経緯

親プロジェクトは、フィジカルAIの開発に必要な技術スタックを、ROS 2の最低限の構成（WSL2 + Ubuntu 24.04 + ROS 2 Jazzy）で一通り身に着ける教材である。慣性のある車両を目標の速度に追従させるシミュレーション（最初のゴール）と、その制御を強化学習で学習させたNNに置き換えること（最終ゴール）を、1つの完成形として作りきる構成にしている。

このプロジェクトは、その派生として、次を作る（2026-10-30、ユーザーの依頼）。

- **題材**: ドローンの3Dシミュレーション
- **使う技術**: PX4（フライトコントローラのソフトウェア）・Gazebo（3Dの物理シミュレータ）・ROS 2
- **やりたいこと**: 3Dの環境でドローンを飛ばし、障害物をセンサで検知したら、経路計画を更新する
- **目的**: ドローンのシミュレーション環境を段階的に構築して動かすこと。ROS 2の基礎の学習は少なめにし、既存のパッケージを活用する。ただし、自作のノードが必要になる場合は、親プロジェクトのフェーズ1の一部を作り直したものと、QoSの復習を用意する（2026-10-30、ユーザーの追加の指示）
- **進め方**: 基本的に親プロジェクトと同じ（役割分担・手順書の書き方・記録・公開の点検は [`CLAUDE.md`](../CLAUDE.md)）
- **想定する学習者**: 親プロジェクトと同じレベル（ROS 2に初めて触れる人）
- **親プロジェクトとの違い**: フェーズ2〜4の内容は親プロジェクトを参照する。ゴールが違う。基本的な用語の解説と環境構築の手順は作り直す
- **開発の形**: 親プロジェクトと同じWSL2の上で開発する。開発中は互いのフォルダを読んでよい。読者は、GitHubを通じて親プロジェクトとの関係を知る

## 5. 確かめる必要がある技術的な事実

ここに書いたことは、2026-10-30の時点で**確かめていない**。手順書に書く前に、それぞれの安定版の公式の文書（PX4のユーザーガイドの安定版、Gazebo Harmonicの文書、ROS 2 Jazzyの文書）とローカルの実物で確かめる。検索の要約や開発版の文書で要件を判断しない（親プロジェクトで、別のツールのベータ版の要件を取り違えた前例がある）。

### 5-1. PX4・Gazebo・ROS 2

- **対応する組み合わせ**: PX4の安定版が、Ubuntu 24.04・ROS 2 Jazzy・Gazebo Harmonic（親プロジェクトの環境。`ros-jazzy-ros-gz` で入るGazebo）の組み合わせに対応しているか。PX4のSITLが使うGazeboと、`ros_gz` が使うGazeboの版が一致するか（一致しないと、ブリッジでセンサのトピックを中継できない）
- **PX4のビルドの要件**: 付属の環境構築のスクリプトが何を入れるか（aptのパッケージ・Pythonのパッケージ・Gazeboの版。既に入っているROS 2のGazeboと衝突しないか）。ディスクの空きとメモリの目安。メモリの少ないPCや、WSL2のメモリを既定の設定のまま使う場合に、ビルドの並列数を絞る必要があるか
- **画面なしの起動**: PX4のSITLとGazeboを、ウィンドウを開かずに起動する方法（PX4の環境変数 `HEADLESS` 等とされる）。センサの描画が画面なしでも動くか
- **センサ**: PX4に付属するGazeboの機体の模型に、センサ付きのもの（深度カメラ付き・LiDAR付き等）があるとされる。名前と中身（どのセンサ・どのトピック）を、使う版のソースで確かめる
- **uXRCE-DDS**: PX4の中のクライアントと、PC側のMicro XRCE-DDS Agentの関係。Agentの導入方法（ソースからのビルドか、パッケージか）。どのPX4のトピックがROS 2に出るかの設定（PX4のソースの中の設定ファイル）
- **`px4_msgs` の版**: PX4のファームウェアの版と `px4_msgs` の版（ブランチ）を合わせる必要があるか。新しい版のPX4にはメッセージの版の仕組みがあるとされるので、その扱い
- **QoS**: PX4が出すトピックのQoSと、ROS 2のノードの購読で指定すべきQoS（親プロジェクトのフェーズ3-2bとのつながり）
- **座標系**: PX4はNED（北・東・下）とFRD（前・右・下）、ROS 2の慣習はENU（東・北・上）とFLU（前・左・上）。どこで変換するか、変換を手順書でどう説明するか。Gazeboのワールドの座標との関係
- **オフボード制御の条件**: PX4をオフボードのモードに切り替えて飛ばすには、切り替えの前から、決まった周期以上で指令を送り続ける必要があるとされる。周期・アームの手順・送り続けないとどうなるか（フェイルセーフ）
- **時刻**: PX4・Gazebo・ROS 2のノードの間で、シミュレーションの時刻をどう扱うか（`use_sim_time`。親プロジェクトのTips集のシミュレーション時刻の項目）
- **PX4に組み込みの衝突防止**: PX4自体に、距離センサの値で前進を止める機能（Collision Prevention）があるとされる。教材の経路計画と役割が重ならないように、使うか切るかを決める。PX4の旧い障害物回避（PX4-Avoidance）はROS 1向けで、使わない見込み
- **QGroundControl**: 地上局のソフトウェア。必須にするか（パラメータの確認・機体の状態の表示に使える）、使わずに済ませるか。WindowsとWSLのどちらで動かすか

### 5-2. 分けて起動する方法（ユーザーのシミュレーションと混ざらないように）

親プロジェクトでは、Claudeが確かめるとき、Gazeboは `GZ_IP=127.0.0.1`・`GZ_PARTITION=<別の名前>`、ROS 2は `ROS_AUTOMATIC_DISCOVERY_RANGE=LOCALHOST`・`ROS_DOMAIN_ID=<別の番号>` で分けた。PX4のSITLは、これに加えて、MAVLinkとuXRCE-DDSのUDPのポートを使う。ユーザーが同時に練習で動かしているPX4・Agentとポートがぶつからない分け方（PX4のインスタンスの番号・Agentのポート・`ROS_DOMAIN_ID` とPX4の設定の関係）を確かめてから、起動する。

## 6. 親プロジェクトで得た知見（引き継ぐもの）

Claudeの作業メモにあった知見のうち、このプロジェクトでも効くものを、一般的な書き方にして写す。

### 6-1. 確かめ方

- **サンプルは使い捨ての環境で確かめてから書く**。手順書のコードブロックの直前に「ファイル: 」の行を置き、そこから使い捨てのワークスペースへ抜き出して `colcon build`、Pythonの `import`、`ros2 launch ... --show-args` / `--print`（起動しない読み込み）まで確かめる。ツールのCLIの挙動（オプション・表示）も、断定する前に使い捨ての環境で動かす。
- **Gazeboを画面なしで確かめる**: `gz sim -s`（サーバーだけ）と、手で起動した `ros_gz_bridge` の `parameter_bridge` で、トピックの値まで確かめられる（デモのlaunchはGUIを開くので使わない）。画面の見え方は確かめられないので、手順書には「画面の見え方は未確認」と書く。
- **止め方**: `gz sim` は `timeout` のSIGTERM・SIGINTを無視して残ることがあるので、`timeout -k 5 -s INT <秒>` の形にする。launchの `Shutdown` でもGazeboのサーバーが残ることがある。`pkill -f` は使わない（ツール自身のシェルや、ユーザーの同名のプロセスにも一致して止めてしまった）。起動した直後の `$!` でPIDを控えるか、`ps -eo pid,ppid,cmd` で確かめてから `kill -INT <PID>` する。シェルの関数の中の `wait` は `wait <PID>` で対象を限る。確認の後は、残りのプロセスと、使った番号の `ros2 daemon` を止めたかを確かめる。
- **ログを外に出さない**: ROS 2は `~/.ros/log/`、Gazeboは `~/.gz/sim/log/` と `~/.sdformat/sdformat.log` にログを書く。確かめる実行では、最初のros2のコマンドより前に `ROS_LOG_DIR` を使い捨ての場所に向け、Gazeboの起動には `HOME`・`GZ_HOMEDIR` を使い捨ての場所に向ける。PX4のSITLも、ビルドのフォルダの中にログとパラメータを書くとされるので、置き場所を確かめる。
- **Gazeboの導入直後のシェル**: 導入の前から開いているシェルでは `gz` が見つからないことがある（`source /opt/ros/jazzy/setup.bash` をし直すと使える）。Gazeboのvendorのフォルダの下は `find` が遅いので、`dpkg -L <パッケージ名>` で探す。`find /` のようにルートから探さない（WSLでは `/mnt/c` まで走査する）。
- **WSLの壁時計が飛ぶ**: 親プロジェクトの作成環境では、WSLの時計が約36秒ごとに約3.6秒進んだ。経過時間は単調な時計（`STEADY_TIME` 等）で測り、ログの時刻の飛びをノードの停止と取り違えない。
- **長い実行は `/tmp` の外に**: Claudeのscratchpadは `/tmp` の下で、日付が変わると消えることがある。長いシミュレーションの結果などは、ホームの下の作業用のフォルダに置き、終わったら消す。
- **URLの確かめ方**: docs.ros.orgはボット対策でWebFetchが本文を取れない。URLの実在は、検索か、GitHubの文書の原稿で確かめる。リンクは推測で書かず、実在を確かめたものだけを載せる。
- **時間のかかる題材は、先に安い予備の実験で差が出るかを確かめる**（`learning-text-authoring` スキル）。

### 6-2. 書き方（手順書）

`CLAUDE.md` と `learning-text-authoring` スキルにあるもののほか、親プロジェクトでユーザーから指摘を受けて決めたこと。

- 動機づけ・概要の節は、箇条書きでなく、読者の状況に引き寄せた文章にする。
- 理解に要る情報を、後の節や前提に無い文書へ送らない。初出の用語には1文の定義を置く。
- 規格用語の詳細や、ほかの方式との比較（例: MAVROSとuXRCE-DDSの比較の細部）は、本文では本質だけにし、Tips集へ移してリンクする。
- 読者が書き込む空欄の表を置かない。
- 一般的な慣習から外れるサンプルには、「一般的な書き方」「このサンプルで変えた理由」「実務での目安」を分けて補足する。一般論の断定はAPIで確かめる。
- 文書を「冊」と数えない（「このページ」「各ページ」）。
- 「あると便利」なだけの相互リンクは足さない（管理の手間が増える）。
- 1件の構造的な不具合を直したら、ほかのページにも同じ原因で残っていないかを機械的に探す。
- GitHubの数式（`$…$`）・mermaidの表示の罠は `markdown-mermaid` スキルにある（全角文字の直後の `$`、`\,` 等の「`\`＋記号」、`^*`、ラベルの「1. 」）。

### 6-3. 図

- WSLにはSVGのレンダラが無い。図は生成スクリプトで作り、すべての文字の一覧とviewBoxからのはみ出し、四角・文字・矢印の交差を機械的に点検する。前の図の生成スクリプトを写して作るときは、前の図の描画の呼び出しを残さない。区分の背景の四角は、矢印より先に描く（後に描くと矢印が隠れる）。目視はユーザーに頼む。

### 6-4. 操作の承認

- ノード・Gazebo・（このプロジェクトでは）PX4のSITLとAgentの起動は、毎回、目的と影響を説明して承認を得る。別の質問への回答から承認を推し量らない。承認はQA表に独立した行で残す。
- aptの導入は、`apt-get install -s`（試すだけ）も含めてClaudeが実行しない（親プロジェクトでは自動の判定でも拒否された）。導入は、ユーザーが自分のターミナルで行う。
- シェルの履歴（`~/.bash_history`）は、目的と範囲を示して承認を得てから読む。
- 作業ディレクトリの外のファイルをBashで読むときは、読む前に目的と範囲を一言書く（親プロジェクトのフォルダを読むときも同じ）。
- 過去の履歴を書き換える操作（amend・rebase・force push等）は、ハーネスに拒否される。必要になったら、`git-history-rewrite` スキルに従い、ユーザーのターミナルで実行してもらう。

### 6-5. 公開

- 親プロジェクトでは、Public化の前に、全履歴の機密スキャン（author・committerのメールを含む）・第三者の著作物の棚卸し・リンクの点検を行い、結果を `docs/public_release_review.md` の実施記録に残した。以後もpushのたびに点検を記録している。このプロジェクトでも、最初のpushから同じ運用にするのがよい（親プロジェクトでは、最初に実メールが履歴に入り、後から全履歴を書き換えた）。
- 作成に使ったPCの用途を、点検の観点の文書やQA表で例示しない（一般的な書き方にする）。
- QA表に、GitHubのアカウント名・PCの実測値・ドライブのパスを書かない（著作権者の表記を決めた行は例外）。
