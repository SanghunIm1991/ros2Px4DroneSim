# 親プロジェクトからの申し送り

このプロジェクト（`ros2Px4DroneSim`）を立ち上げるときに、親プロジェクトの [`ros2MinimalPhysicalAi`](https://github.com/SanghunIm1991/ros2MinimalPhysicalAi) から引き継ぐ事項をまとめた文書。教材の本文ではなく、計画と記録の文書として扱う（READMEの「計画と記録の文書」に載せた）。

作成: 2026-10-30（親プロジェクトのセッションで作成）

## 1. 目的と経緯

親プロジェクトは、フィジカルAIの開発に必要な技術スタックを、ROS 2の最低限の構成（WSL2 + Ubuntu 24.04 + ROS 2 Jazzy）で一通り身に着ける教材である。慣性のある車両を目標の速度に追従させるシミュレーション（最初のゴール）と、その制御を強化学習で学習させたNNに置き換えること（最終ゴール）を、1つの完成形として作りきる構成にしている。

このプロジェクトは、その派生として、次を作る（2026-10-30、ユーザーの依頼）。

- **題材**: ドローンの3Dシミュレーション
- **使う技術**: PX4（フライトコントローラのソフトウェア）・Gazebo（3Dの物理シミュレータ）・ROS 2
- **やりたいこと**: 3Dの環境でドローンを飛ばし、障害物をセンサで検知したら、経路計画を更新する
- **目的**: ドローンのシミュレーション環境を段階的に構築して動かすこと。ROS 2の基礎の学習は少なめにし、既存のパッケージを活用する。ただし、自作のノードが必要になる場合は、親プロジェクトのフェーズ1の一部を作り直したものと、QoSの復習を用意する（2026-10-30、ユーザーの追加の指示）
- **進め方**: 基本的に親プロジェクトと同じ（役割分担・手順書の書き方・記録・公開の点検は [`CLAUDE.md`](../CLAUDE.md)）
- **想定する学習者**: 親プロジェクトと同じレベル（ROS 2に初めて触れる人）
- **親プロジェクトとの違い**: フェーズ2〜4の内容は親プロジェクトを参照する。ゴールが違う。基本的な用語の解説と環境構築の手順は作り直す
- **開発の形**: 親プロジェクトと同じWSL2の上で開発する。開発中は互いのフォルダを読んでよい。読者は、GitHubを通じて親プロジェクトとの関係を知る

### 3-2. 目的・ゴール・段階

- ROS 2の基礎の学習は少なめにし、既存のパッケージを活用する。自作のノードが要る場合は、親プロジェクトのフェーズ1の一部の作り直しと、QoSの復習を用意する（2026-10-30、ユーザー判断）

- 想定する学習者は、ドローンとPX4については素人で、教育資料として丁寧に進める（2026-10-31、ユーザー判断）
- 段階は次の6つ（2026-10-31、ユーザー判断）。自作のノードが要るのは③と⑥の見込み。
  - ① PX4とGazeboで、ドローンを離陸・移動・着陸させる（最初のゴール）
  - ② ROS 2から機体の状態を見る
  - ③ ROS 2から指令して飛ばす（オフボード制御）
  - ④ センサ付きの機体と障害物のワールドで、センサの値をROS 2で見る
  - ⑤ PX4に組み込みの衝突防止を試す（Position modeで手動で飛ばし、障害物の手前で減速・停止する。経路は計画し直さない）
  - ⑥ 障害物を検知したら、経路を計画し直して回避する（最終ゴール）
- フェーズの番号は段階の番号にそろえる（フェーズ1〜6）。その前に環境構築とフェーズ0（ドローンとPX4の用語と仕組みの読み物）を置く。必須は環境構築とフェーズ0〜6、任意は間章（深度カメラ）とTips集。状況に応じて柔軟に直す（2026-10-31、ユーザー判断。詳細は [`docs/learning_plan.md`](learning_plan.md)）

- 親プロジェクトのフェーズ5-4は、参考のリンクを置くだけにし、前提として読者を送らない（車両の制御の文脈が大半で混乱させるため）。`ros_gz_bridge` の部分は、重複してもフェーズ4で書き直す（2026-10-31、ユーザー判断）。同じ考え方を、文脈が違う親プロジェクトの章（例: 2節の表のフェーズ5-0）にも当てはめる（Claude判断）

### 3-3. 技術の選定

いずれも2026-10-31のユーザー判断（Claudeが示した推奨・選択肢の説明の中身を含めて承認されたもの）。

- **PX4の版**: 安定版v1.17で始める（`px4_msgs` は `release/1.17`）。ROS 2 Jazzyとの組み合わせは、v1.17の文書では推奨されていないので、②の前に予備の実験で確かめる。v1.18が安定版になったら、上げるかを改めて決める
- **ROS 2とのつなぎ方**: uXRCE-DDSだけを使う。MAVROSは、Tips集で違いと使いどころを紹介するに留める
- **QGroundControl**: 全段階で必須にする（WSLの中のAppImage版）。既定では、地上局か送信機がつながっていないとアームできず（③・⑥のオフボード制御も同じ）、⑤も手動の操縦の入力が要るため（5-0）。当初は「①だけで使い、②以降は必須にしない」と決めたが、レビューでこの要件が分かり、決め直した
- **センサ**: 2DのLiDAR（`gz_x500_lidar_2d`）。作成に使ったPCで動くか・画面なしで値が出るかを、④の前に予備の実験で確かめる。障害物は、同じ高さを飛んで水平に避ける形に限る。深度カメラは、後から間章として作るかもしれない
- **経路計画**: ⑥を検討するときに、既存のパッケージを使えないかを実験で確かめてから決める。2026-10-31の調べでは、Aerostack2はJazzy向けのaptのパッケージが無く、Nav2は地上のロボット向け、`ros-jazzy-octomap-server` は地図だけだった。自作の簡単な計画器（格子の地図とA*など）は、既存のもので足りない場合の案
- **言語**: Pythonを優先し、最終ゴールまでPythonで作り切る。必要に応じて、後からC++を付け加える余地を残す
- **図の形式・実行の確認の範囲・READMEの「確認した環境」**: 親プロジェクトと同じ。確認の範囲は、ユーザーがPX4をビルドした後に、Claudeが毎回承認を得て、PX4のSITLとGazeboを画面なしで起動して確かめる（ユーザーの練習と分ける方法は5-2を先に確かめる）。確認した環境は、READMEの1か所だけに載せる

### 3-4. 環境

- 既に入っているROS 2 JazzyとGazebo（親プロジェクトのために入れたもの）を共通で使い、環境は分けない。分ける必要が出たら相談する（2026-10-31、ユーザー判断）
- PX4のソースは `~/PX4-Autopilot`、PX4専用のvenvは `~/px4-venv`（`--system-site-packages` 付き）。`ubuntu.sh` は、このvenvを有効にしてから、`--no-nuttx` を付けて実行する（2026-10-31、ユーザー判断）

- マイコン向けのツールチェーンは入れない。導入の方法と使い方はTips集に書く（2026-10-31、ユーザー判断）

5-0は、2026-10-31に確かめた結果。5-1は、2026-10-30に「確かめる必要がある」と挙げた項目で、各項目の末尾に今の状態を書いた。手順書に書く前に、それぞれの安定版の公式の文書（PX4のユーザーガイドの安定版、Gazebo Harmonicの文書、ROS 2 Jazzyの文書）とローカルの実物で確かめる。検索の要約や開発版の文書で要件を判断しない（親プロジェクトで、別のツールのベータ版の要件を取り違えた前例がある）。

### 5-0. 確かめた結果（2026-10-31）

PX4の安定版の文書（PX4-Autopilotのリポジトリの `release/1.17` のブランチの `docs/en/`）と、GitHubの公開の情報で確かめた。以下は要約で、手順書に書くときは、その時点の文書で改めて確かめる。

- **PX4の版**: 最新の安定版はv1.17.0（2026-05-13）。v1.18は候補版（rc1、2026-09-10）で、まだ安定版ではない（GitHubのリリースの一覧）。
- **Ubuntu 24.04とGazebo**: v1.17の文書は、PX4の開発環境の対象にUbuntu 24.04を含め、24.04ではGazebo Harmonic・Ionic・Jettyに対応するとしている（入っている最新のものが使われる）。導入は付属の `Tools/setup/ubuntu.sh` で行う。
- **ROS 2 Jazzy**: v1.17の文書は、PX4と使うROS 2の推奨を「Humble（Ubuntu 22.04）」としている。開発版（`main`）の文書では、推奨が「Jazzy（Ubuntu 24.04）」に変わっている。ROS 2の側がPX4に依存するのはメッセージの定義（`px4_msgs`）だけで、`px4_msgs` にはPX4の版ごとのブランチ（`release/1.17` 等）がある（GitHubのブランチの一覧）。v1.16から、メッセージの版の仕組みと、版が違うときに変換するノード（Message Translation Node）がある。v1.17の文書の手順は `px4_msgs` を既定の `main` のままcloneする形なので、手順書では `release/1.17` を明示する。v1.17とJazzyの組み合わせは、予備の実験で確かめる。
- **起動**: `make px4_sitl gz_x500` で、PX4のSITLとGazeboが一緒に起動する。`HEADLESS=1` を前に付けると画面なしで起動する。ワールドは名前を付け足す（`gz_x500_walls` 等）か、`PX4_GZ_WORLD` で選ぶ。
- **センサ付きの機体**: `gz_x500_depth`（前向きの深度カメラ）・`gz_x500_lidar_2d`（2DのLiDAR。0.1〜30mの範囲を、270°の弧で測る）・`gz_x500_lidar_front`・`gz_x500_lidar_down`（1DのLiDAR、前向き・下向き）などがある。ワールドには、衝突防止を試すための壁のワールド `walls` がある。模型とワールドは、PX4のリポジトリのサブモジュール（Gazeboの模型のリポジトリ）から入る。
- **uXRCE-DDS**: PX4のSITLは、起動するとuXRCE-DDSのクライアントを自動で始め、ローカルのUDPの8888番のポートのAgentにつなぐ。Agentは、ソースからのビルド（文書の例は `v2.4.3`）か、snapで入れる。ROS 2の側のトピックの名前は、型の版（`MESSAGE_VERSION`）が0でないと、末尾に `_v<版>` が付く（v1.17のソースの `src/modules/uxrce_dds_client/utilities.hpp` で確かめた。例: `/fmu/out/vehicle_status_v1`・`/fmu/out/vehicle_local_position_v1`。`vehicle_odometry` と `trajectory_setpoint` は版が0なので付かない。2026-10-31、フェーズ0の作成時）。

- **アームの条件**: 既定では、地上局（QGC）かRCの送信機がつながっていないとアームできない（手動で取り戻す手段を常に残すため）。オフボード制御の例の文書も、ノードを動かす前にQGCをつなぐよう注意している。
- **公開のサンプル**: `px4_ros_com` に、受信（`sensor_combined_listener` 等）と、オフボード制御のサンプル（C++の `offboard_control.cpp`。`main` のブランチのファイルの一覧では、Pythonの `offboard_py/offboard_control.py` もある）がある。PX4の文書は、Pythonの例として、第三者のリポジトリ `Jaeyoung-Lim/px4-offboard` を案内している（使う場合は権利を確かめる）。オフボード制御のサンプルは、指令を送り始めてからオフボードのモードに切り替えてアームし、5m上昇して待つだけ。PX4は、`OffboardControlMode` が約2Hzを下回ると、オフボードのモードから抜ける。
- **組み込みの衝突防止（Collision Prevention）**: マルチコプターのPosition mode（操縦の入力で飛ばすモード。`MPC_POS_MODE` を加速度ベースにする）で使える。オフボードの飛行では使わない。障害物に近づくと速度を制限して減速・停止し、障害物との距離を `CP_DIST` 以上に保つ。より良い方向が近くにあれば、入力の向きを `CP_GUIDE_ANG` の範囲で少し補正して、障害物に沿わせる。経路を計画し直しはしない。センサの値が無い方向へは動けない（`CP_GO_NO_DATA` で変えられる。`gz_x500_lidar_2d` は270°しか測らないので、既定では後ろへ動けない）。距離の値が0.5秒途切れると水平の移動を止め、5秒でHOLDのモードに入る。Gazeboでは `gz_x500_lidar_2d` で試せる。

- **Gazeboが2通り入る**: `ros-jazzy-ros-gz` だけでGazeboを入れた環境では、GazeboはROS 2のvendorのパッケージ（`ros-jazzy-gz-*-vendor`）として入り、Gazebo公式のaptのリポジトリは登録されない。そこで `ubuntu.sh` を実行すると、同じHarmonicが、vendorのものとGazebo公式のものの2通り入る。どちらの `gz` が使われるか・PX4がどちらでビルドされるか・`ros_gz_bridge` とつながるかは、予備の実験で確かめる。

### 6-1. 確かめ方

- **サンプルは使い捨ての環境で確かめてから書く**。手順書のコードブロックの直前に「ファイル: 」の行を置き、そこから使い捨てのワークスペースへ抜き出して `colcon build`、Pythonの `import`、`ros2 launch ... --show-args` / `--print`（起動しない読み込み）まで確かめる。ツールのCLIの挙動（オプション・表示）も、断定する前に使い捨ての環境で動かす。
- **Gazeboを画面なしで確かめる**: `gz sim -s`（サーバーだけ）と、手で起動した `ros_gz_bridge` の `parameter_bridge` で、トピックの値まで確かめられる（デモのlaunchはGUIを開くので使わない）。画面の見え方は確かめられないので、手順書には「画面の見え方は未確認」と書く。
- **止め方**: `gz sim` は `timeout` のSIGTERM・SIGINTを無視して残ることがあるので、`timeout -k 5 -s INT <秒>` の形にする。launchの `Shutdown` でもGazeboのサーバーが残ることがある。`pkill -f` は使わない（ツール自身のシェルや、ユーザーの同名のプロセスにも一致して止めてしまった）。起動した直後の `$!` でPIDを控えるか、`ps -eo pid,ppid,cmd` で確かめてから `kill -INT <PID>` する。シェルの関数の中の `wait` は `wait <PID>` で対象を限る。確認の後は、残りのプロセスと、使った番号の `ros2 daemon` を止めたかを確かめる。
- **ログを外に出さない**: ROS 2は `~/.ros/log/`、Gazeboは `~/.gz/sim/log/` と `~/.sdformat/sdformat.log` にログを書く。確かめる実行では、最初のros2のコマンドより前に `ROS_LOG_DIR` を使い捨ての場所に向け、Gazeboの起動には `HOME`・`GZ_HOMEDIR` を使い捨ての場所に向ける。PX4のSITLも、ビルドのフォルダの中にログとパラメータを書くとされるので、置き場所を確かめる。
- **Gazeboの導入直後のシェル**: 導入の前から開いているシェルでは `gz` が見つからないことがある（`source /opt/ros/jazzy/setup.bash` をし直すと使える）。Gazeboのvendorのフォルダの下は `find` が遅いので、`dpkg -L <パッケージ名>` で探す。`find /` のようにルートから探さない（WSLでは `/mnt/c` まで走査する）。
- **WSLの壁時計が飛ぶ**: WSLでは、壁時計（日時の時計）が、ときどき数秒まとめて進むことがある。経過時間は単調な時計（`STEADY_TIME` 等）で測り、ログの時刻の飛びをノードの停止と取り違えない。
- **長い実行は `/tmp` の外に**: Claudeのscratchpadは `/tmp` の下で、日付が変わると消えることがある。長いシミュレーションの結果などは、ホームの下の作業用のフォルダに置き、終わったら消す。
- **URLの確かめ方**: docs.ros.orgはボット対策でWebFetchが本文を取れない。URLの実在は、検索か、GitHubの文書の原稿で確かめる。リンクは推測で書かず、実在を確かめたものだけを載せる。
- **時間のかかる題材は、先に安い予備の実験で差が出るかを確かめる**（`learning-text-authoring` スキル）。
