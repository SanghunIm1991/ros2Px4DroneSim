## 1. 目的と位置づけ

- **目的**: 新しい機体を開発するときに、Gazeboの模型とPX4の設定のどこを触るべきかを知ること（2026-11-22、ユーザー判断）。
- **値の決め方**: 諸元から計算した値に限らず、推定や実験で決めた値を含めてよい。条件は、実際に試して安定して飛ぶこと。
- **前提**: 間章「機体を定義する」（`docs/interlude_custom_sensor.md`。下書き）。案2で使う2〜4節（模型の3段の重なり・名前の約束・何を変えるとどこを合わせるか）は、ソースと画面なしの起動で確かめ済みなので、画面の確認など（`dev/pending_checks.md` の5項目のうち4つ）は後回しにして前提として扱う。残りのうち5-2節の `git status` の表示（`Tools/simulation/gz (untracked content)`）は、案2の片付けの確認（4節）の中で確かめる（2026-11-22、ユーザー判断）。
- **扱わないもの**: センサの部品。メッシュ（ユーザーの別のリポジトリで扱う予定）。制御工学の設計（用語を並べる程度にする）。

## 2. 決まったこと（2026-11-22）

## 4. 作る前に確かめること

- [ ] **権利の再確認**（ユーザーの指示「出典について権利の問題がないか作成前に再度調べてください」）: PX4の文書（CC BY 4.0）、4052番の機体の設定（BSD 3-Clause。値を見比べるのは事実の利用だが、ファイルを抜粋するならライセンスの表示が要る）、Holybroの製品のページ（リンクと値だけにする）、モーターの製造元の資料（推力の試験表を使う場合）、x500の模型（BSD 3-Clause。構造を参考にする場合）。結果はQA表に残す
- [ ] **諸元の出どころ**: 重さ（全体・部品ごと）・ホイールベース・モーターの推力。PX4の文書が案内する今の製品のページ（`holybro.com/products/qav250-kit`）で確かめる（アクセスの制限〈HTTP 429〉が出たら再試行せず、別の出どころに切り替える）。公式の資料に無いものは、推定の方法を決める
- [ ] **`PX4_PARAM_` の働き**: 画面なしの起動で確かめる（`make` の起動でも効くか、値が `parameters.bson` に保存されるか、借りた番号の機体の設定の既定とどちらが勝つか）
- [ ] **環境変数が残る問題**（セッションのレビューの指摘M2）: `PX4_PARAM_` を `export` したターミナルで本編の機体を起動すると、その値が本編の機体にも設定される（`rcS` の129〜136行は、番号が変わって既定に戻した後に働く）。専用のターミナルにする、`unset` の手順を書く、起動を1行（`env PX4_PARAM_…=… make …` 等）にする、のどれにするかを作るときに決め、実際に確かめる
- [ ] **既定に戻らない値**（同じ指摘）: 番号が変わったときの `param reset_all` は、`RC*`・`CAL_*`・`COM_FLTMODE*`・`LND_FLIGHT*`・`TC_*`・`COM_FLIGHT*` を除く（`rcS` の125行）。値の一覧にこれらの名前を入れないか、入れるなら個別に戻す手順を書く
- [ ] **借りる番号**: 本編で使わないgz用の番号のうち、機体の設定の既定が少ないもの（候補を比べる）
- [ ] **小さな機体のシミュレーション**: Gazeboの時間の刻み（ワールドの設定）で、小さく軽い機体が安定して計算できるか
- [ ] **片付けの手順**: 実際に片付けて、`git status` に何も残らないこと、本編の機体で起動して値が既定に戻ることを確かめる

## 5. 進め方

1. 4節を確かめ、この文書に結果と、細部（節の構成・慣性の計算・推力の係数の推定・「安定」の基準）の案を書き、ユーザーに示す。
2. 着手の指示を受けてから、模型と値の一覧を作り、画面なしの起動で安定して飛ぶまで確かめる（起動のたびに承認を得る）。
3. 手順書の下書きを書き、文脈を持たないサブエージェントのレビューを通す。
